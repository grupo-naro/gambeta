El problema a resolver

El complejo opera hoy con reservas manuales por WhatsApp: una persona del equipo lee mensajes, consulta disponibilidad, responde y confirma. Esto tiene tres problemas críticos:

🕐 Demoras
Los clientes esperan respuesta. Si nadie atiende rápido, buscan otra cancha.
📋 Errores
Doble reserva del mismo turno, pérdida de mensajes, sin historial organizado.
📊 Sin datos
No hay analíticas de ocupación, horarios pico ni ingresos proyectados.

La solución en una línea

Un bot de WhatsApp que entiende lenguaje natural, consulta disponibilidad en tiempo real, confirma reservas automáticamente y permite al equipo administrar todo desde un panel web.

1
Conexión WhatsApp

Esta es la decisión más crítica del proyecto. Hay dos caminos con trade-offs muy distintos entre velocidad de implementación, costo y estabilidad a largo plazo.

⭐ Recomendado
Evolution API
Open source — autohosteado en VPS con Docker
Servidor Node.js open-source que mantiene una sesión activa de WhatsApp Web y expone una REST API con estructura idéntica a la oficial de Meta. Tiene integración nativa con n8n, lo que hace el setup extremadamente directo. Para activarlo solo hay que escanear un QR con el número del negocio. Sin verificación de empresa, sin aprobación de plantillas, sin costos por conversación.
$5–10/mes en VPS Deploy con Docker Webhooks en tiempo real Nodo nativo n8n Sin costo por mensaje QR scan setup
⚠️
Riesgo a tener en cuenta: Usa WhatsApp Web, no la API oficial de Meta. Si se detecta volumen muy alto o comportamiento claramente automatizado, Meta puede restringir el número. Para un complejo deportivo con volúmenes moderados y respuestas naturales (con delays simulados entre mensajes), el riesgo es bajo. Mitigación: nunca enviar mensajes masivos proactivos, solo responder conversaciones iniciadas por el usuario.
Meta WhatsApp Business Cloud API
Oficial — vía Meta Developers o BSP
La API oficial de Meta. Requiere verificación del negocio (puede tardar semanas), aprobación de plantillas para mensajes proactivos (recordatorios), y cobra por conversación. En Argentina el costo es aproximadamente $0.03–0.06 USD por conversación de servicio. Más estable a largo plazo, pero más burocracia para arrancar.
~$0.03–0.06 / conversación Verificación Meta requerida Templates aprobados 100% estable Sin riesgo de ban
💡
Decisión práctica: Para arrancar rápido y probar el sistema con el cliente, Evolution API es el camino correcto. Si en el futuro el negocio escala significativamente o el cliente pide garantías formales, migrar a la API oficial de Meta con un BSP (proveedor autorizado). La arquitectura soporta ese cambio sin tocar el resto del stack.
2
Motor de automatización

n8n es el cerebro que conecta WhatsApp, la IA, la base de datos y el backend. Es una herramienta de automatización visual (similar a Zapier o Make) pero open-source y autohosteada, lo que significa cero costos por ejecución.

⭐ Recomendado
n8n self-hosted
Gratis — en el mismo VPS, Docker compose
Corriendo en tu propio servidor: sin límites de workflows, sin costos por ejecución, datos en tu infraestructura. La combinación n8n + Evolution API es actualmente la más popular en la comunidad para automatizar WhatsApp en proyectos técnicos. Soporta memoria conversacional vía LangChain, Code Nodes con JavaScript para lógica custom, y conexión directa a PostgreSQL.
$0 en ejecuciones Sin límite de workflows Nodo Evolution API nativo LangChain memory Code nodes JS/Python Nodo PostgreSQL directo
n8n Cloud
Desde $20/mes — sin gestionar infraestructura
Si no querés ocuparte del servidor. El plan Starter incluye 2,500 ejecuciones/mes — un chatbot activo puede consumir eso en pocos días (cada mensaje = 1 ejecución). El plan Business escala pero sube el costo. Viable si el cliente paga bien y no hay tiempo para DevOps.
Desde $20/mes Límite de 2,500 ejecuciones Sin DevOps Deploy instantáneo
Make (Integromat)
No recomendado — cobra por operación, no por ejecución
Cobra por cada operación dentro del workflow. Una sola conversación puede consumir 10–20 operaciones (recibir mensaje, llamar IA, consultar DB, escribir DB, responder). Escala muy mal en precio para chatbots activos.
Caro a escala Cobra por operación
3
Modelo de Inteligencia Artificial

El modelo de IA hace dos cosas: parsea el lenguaje natural del usuario ("quiero la cancha 2 el viernes a las 8") para extraer fecha, hora y cancha, y genera respuestas naturales en español. Para un bot de reservas, no se necesita el modelo más potente — se necesita el más económico que entienda bien español.

Un buen system prompt reduce el costo de tokens y mejora la precisión del bot.
4
Backend Node.js + Base de Datos

El backend maneja la lógica de negocio que n8n no debería hacer directamente: verificar disponibilidad, prevenir doble reserva, gestionar cancelaciones y exponer datos al panel de administración.

🔧 Servidor Node.js
API REST en Express o Fastify con TypeScript. Expone endpoints para n8n (verificar disponibilidad, crear reserva) y para el panel de admin (CRUD completo, analíticas).
Express / Fastify TypeScript REST API JWT auth para panel
🗄️ Base de Datos
PostgreSQL para persistencia de reservas y usuarios. Redis para la memoria conversacional del bot (contexto de cada sesión de WhatsApp activa).
PostgreSQL Redis (sesiones bot) Supabase free tier OK
💡
Simplificación para el MVP: n8n puede conectarse directamente a PostgreSQL sin pasar por el backend Node.js para los flujos simples de reserva. El backend custom solo es estrictamente necesario para el panel de admin y la lógica de conflictos compleja. Se puede construir en fases.
5
Panel de Administración Interno

Interface web para el equipo del complejo. No es pública — solo acceden los administradores para gestionar turnos, ver analíticas y hacer override manual cuando sea necesario.

📅
Vista Calendario
Semana actual con turnos por cancha. Click en turno para ver datos del cliente y opciones de gestión. Color por estado: confirmado, cancelado, pendiente.
📋
Lista de Reservas
Tabla con filtros por fecha, cancha y estado. Búsqueda por número de WhatsApp o nombre. Cancelación y reasignación manual de turnos.
📊
Analíticas
Ocupación por día y hora (heatmap), ingresos estimados, tasa de cancelación, canchas más demandadas, horarios pico.
Stack sugerido
React + TypeScript + Recharts
Tu stack habitual. Para los charts de analíticas, Recharts es suficiente y simple. Para el calendario, FullCalendar tiene una versión gratuita que funciona bien. Deploy en Vercel o en el mismo VPS.
React + TypeScript Recharts (gráficos) FullCalendar (gratis) Vercel deploy Shadcn/ui para components

Reservas
1
Evolution API — Puerta de entrada WhatsApp
Corre en Docker en el VPS. Mantiene la sesión de WhatsApp activa y reenvía cada mensaje entrante como webhook a n8n. También recibe instrucciones de n8n para enviar respuestas al usuario.
$5–10 / mes VPS
2
n8n self-hosted — Orquestador del flujo completo
Recibe el webhook, gestiona el contexto de la conversación (via Redis), llama a Gemini para parsear el mensaje, consulta disponibilidad en PostgreSQL, confirma la reserva y envía la respuesta de vuelta a WhatsApp. Toda la lógica de flujo vive aquí.
$0 (mismo VPS)
3
Gemini 2.5 Flash — Comprensión de lenguaje natural
Parsea frases libres como "quiero la cancha 2 el viernes a las 8 de la noche" y devuelve JSON estructurado con {cancha, fecha, hora, nombre}. También genera las respuestas conversacionales en español rioplatense según el contexto.
$1–3 / mes
4
PostgreSQL + Redis — Persistencia y memoria
PostgreSQL almacena todas las reservas, canchas y horarios disponibles. Redis guarda el estado de cada conversación activa (para que el bot recuerde lo que se dijo antes en la misma charla). Pueden correr en el mismo VPS o usar Supabase free tier para Postgres.
$0 (mismo VPS)
5
Node.js API — Lógica de negocio y exposición al panel
Valida conflictos de horario, gestiona cancelaciones, envía recordatorios automáticos 24hs antes de cada turno, y expone todos los endpoints REST que consume el panel de administración. Auth con JWT para el acceso del equipo.
$0 (mismo VPS)
6
Panel React — Gestión interna del complejo
Dashboard web para el equipo administrador. Calendario semanal por cancha, listado de reservas con búsqueda y filtros, módulo de analíticas (ocupación, ingresos, horarios pico). Deploy en Vercel o el mismo VPS.
$0 (Vercel free)

Flujo de cobro de seña

Una vez confirmado que el slot está disponible, el sistema bifurca según si el usuario está guardado como contacto en la agenda del número del negocio (Evolution API). Los contactos conocidos reservan directo; los desconocidos deben pagar una seña cuyo comprobante es verificado automáticamente por Gemini.

Contacto registrado
El número del usuario está en la agenda de WhatsApp del negocio. El sistema lo trata como cliente de confianza: confirma el turno directamente sin pedir seña y le envía el resumen de la reserva.
Sin seña Confirmación inmediata Evolution API contacts
Desconocido
El número no está en la agenda. El bot envía el CBU/alias con el monto de seña y un tiempo límite (30 minutos). La reserva queda en estado esperando_sena hasta recibir el comprobante.
Seña requerida Timeout 30 min Estado Redis con TTL
🤖 IA
Verificación automática con Gemini Vision
Cuando el cliente envía el comprobante (imagen o PDF), n8n lo pasa a Gemini con este prompt de sistema. Gemini devuelve JSON estructurado que n8n compara contra los valores esperados en DB:
Analizá este comprobante de transferencia bancaria argentina.
Extraé y respondé SOLO en JSON con estos campos:
{ "monto": number, "cbu_destino": string, "alias_destino": string,
  "fecha": string, "es_comprobante_valido": boolean }
Si no podés leer algún campo, usá null.
Soporta imagen (JPG/PNG) Soporta PDF Respuesta en JSON Aprobación automática si coincide
Escalado a humano
Cuando Gemini no puede verificar
Si el monto no coincide, el CBU es diferente, o el archivo no es legible: n8n notifica al equipo en un grupo de WhatsApp del negocio adjuntando el comprobante, el nombre del cliente y un link directo al panel para aprobar o rechazar. El endpoint es PATCH /reservas/:id/aprobar-sena.
Notificación al grupo WA del equipo Link al panel Aprobación con un click
⏱️
Timeout en Redis: Al enviar el CBU, n8n guarda en Redis la clave sena:{numero_wa} con TTL de 1,800 segundos. Cada mensaje nuevo del usuario se chequea contra esta clave. Si expiró, el bot informa que el tiempo venció y sugiere reiniciar.
🔔
Notificación al equipo: n8n manda al grupo interno de WhatsApp el comprobante adjunto + nombre + número + monto detectado + link al panel. El admin aprueba desde PATCH /reservas/:id/aprobar-sena y el bot confirma automáticamente al cliente.
Roadmap de desarrollo

División en fases para entregar valor rápido al cliente mientras se construye el sistema completo.

1
MVP — Bot básico de reservas
1–2 semanas

El cliente puede hacer y confirmar reservas por WhatsApp. Sin panel aún. Objetivo: validar que el flujo funciona en producción y que el cliente está conforme con la experiencia.

Setup VPS + Docker + Evolution API + n8n
Flujo n8n básico: recibir mensaje → llamar Gemini → devolver respuesta
PostgreSQL con tablas base (canchas, reservas, clientes)
Lógica de disponibilidad: consultar si el horario está libre antes de confirmar
Respuesta de confirmación con resumen de la reserva
Manejo de casos edge: horario no disponible, formato de fecha incorrecto
2
Producción — Backend robusto y memoria
2–3 semanas

Reforzar el sistema para uso real del negocio. Agregar Redis para memoria conversacional, lógica de cancelaciones y recordatorios automáticos.

Redis para memoria de sesión (el bot recuerda el contexto de cada charla)
Node.js backend con lógica de conflictos (prevenir doble reserva concurrente)
Flujo de seña: chequeo de agenda Evolution API, envío de CBU/alias, timeout Redis de 30 min
Verificación de comprobante con Gemini Vision (imagen y PDF)
Escalado a humano con notificación al grupo WA del equipo y endpoint de aprobación manual
Flujo de cancelación: el cliente puede cancelar desde WhatsApp
Recordatorios automáticos 24hs antes del turno
Delay simulado en respuestas (1–3 seg) para comportamiento más natural
Logs de conversación y manejo de errores
3
Panel — Dashboard de administración
2–3 semanas

Interface web para el equipo del complejo. React + TypeScript con calendario visual, gestión de reservas y analíticas de negocio.

Calendario semanal con slots por cancha (FullCalendar)
Listado de reservas con filtros por fecha, cancha y estado
Cancelación y reasignación manual de turnos
Módulo de analíticas: ocupación por hora, canchas más demandadas, ingresos
Auth básico con JWT para el equipo admin
Deploy en Vercel

Tiempo total estimado: 5–8 semanas para el producto completo. El cliente puede estar usando el bot en producción desde la semana 2, mientras se construyen las funciones avanzadas en paralelo.
